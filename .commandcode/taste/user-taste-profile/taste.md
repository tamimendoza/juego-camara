# User Taste Profile
- Uses the OpenSpec framework for formal planning before implementation — creates a change with proposal → spec → design → tasks artifacts, then applies and archives. Confidence: 0.9
- Creates new projects in the current working directory rather than specifying a different path. Confidence: 0.8
- Prefers executable launch scripts (`./run.sh`) as the primary method for running applications, rather than typing Python invocation commands directly — when the script fails, tries `python3 <file>.py` as a fallback rather than module syntax (`python3 -m`). Confidence: 0.75
- Requests internet research to inform tool selection, with tools chosen based on the target operating system (Linux Ubuntu). Confidence: 0.9
- For pose/motion-tracking projects, requires full-body detection covering head, arms, legs, and torso (not just partial body parts). Confidence: 0.7
- Prefers Spanish for communication (user messages initiated in Spanish). Confidence: 0.85
- Prefers stick-figure rendering with camera feed fully removed — a solid background where the person is de-identified via a circle for the head and lines for the body only, explicitly excluding all facial feature rendering (no face skeleton lines or joint dots, filtered at landmark index 11). Confidence: 0.9
- Prefers miniaturized/scaled-down character representations (a "miniatura" of the person) rendered at a small size on screen that mirrors the player's pose via scaled-transformed landmarks, rather than full-size pose rendering. Confidence: 0.8
- CLI arguments use `argparse` with both a short (`-c`) and a long (`--camera`) flag form. Confidence: 0.85
- Shell launch scripts (`run.sh`, `run_game.sh`) forward all arguments transparently to the underlying Python module via `"$@"` so that CLI flags pass through from the wrapper. Confidence: 0.9
- Console diagnostic prints map numeric device indices to their actual Linux device file paths (e.g. `/dev/videoN`), bridging the abstraction so users can correlate with `ls /dev/video*`. Confidence: 0.8
- Prefers snappier, less-floaty game physics — specifically wants a faster falling speed (shorter air-time) rather than extended hang-time, treating jump "feel" as adjustable via gravity tuning. Confidence: 0.75
- Provides iterative, targeted feedback on game parameters — accepts an initial working implementation and then refines specific aspects (e.g., "jump height is fine, but the fall is too slow") rather than specifying all numeric requirements upfront. Confidence: 0.7
- Explicitly requests to be asked clarifying questions ("si tienes dudas me preguntas") when design decisions are ambiguous, preferring to confirm choices before implementation proceeds. Confidence: 0.9
- When explicitly asked to "create a plan" ("crea una plan"), enters structured plan mode — surveys the codebase, asks clarifying questions, writes a detailed plan file, then exits plan mode before any implementation begins. Confidence: 0.85
- Prefers non-breaking separate variants: when asked for "another version of the game," creates new files (e.g. mario_game.py, mario_main.py, run_mario.sh) that reuse shared infrastructure rather than modifying existing game code. Confidence: 0.75
- Prefers test files that mirror the structure and patterns of existing test files (class-based organization, assertion style, mock landmark helpers) so new tests feel consistent with the established suite. Confidence: 0.75
- Uses thicker lines (3px) for character rendering on small miniatura figures to ensure visibility at the scaled-down on-screen size. Confidence: 0.65
- When requirement corrections or clarifications are discovered during implementation (often relayed from stakeholder/end-user feedback), documents them in the OpenSpec artifacts (design.md, spec.md) to keep the spec in sync with the evolving implementation, rather than only making code changes. Confidence: 0.85
- Prefers fixed/predictable sizing for miniatura character rendering — the character must not "amplify" (enlarge or scale up) when pose detection is partial or degrades; rendering size should be capped or normalized regardless of input quality. Confidence: 0.9
- Prefers preserving the last-known pose/state when pose detection degrades (e.g. fewer than ~5 landmarks visible) rather than letting the character jump around, morph, or disappear — the character should "remain still" in its prior state until reliable detection resumes. Confidence: 0.9
- Expects rendering to match the specified primitive — when "rectangle" is specified, uses solid filled rectangles rather than decomposed thin line-segment chains or polylines. Confidence: 0.8
- In pose-tracking miniaturas, the character's torso and body proportions must remain rigid — only arms and legs are permitted to move, and each limb endpoint is clamped to a maximum extension distance from its joint so the character never deforms or stretches beyond a limited range. Confidence: 0.85
- Displays a status/warning message at the top of the screen when pose detection quality is poor (e.g., user too close or too far from the camera), which disappears as soon as the pose is reliably detected again. Confidence: 0.85
- Treats jumping as the primary / most-important interaction in pose-tracking games and gates jump detection on detection quality — jumps only register when the pose is reliably detected (e.g., not when a scale/detection warning is active). Confidence: 0.8
- Expects features to be applied consistently across ALL game variants — when a feature (e.g., sound effects, double jump) is added to one game, the user expects it to work in every variant (Mario, Minecraft, base game). Testing one variant and finding the feature missing in another is treated as a bug requiring immediate fix. Confidence: 0.9
- Tests features through real gameplay execution and provides specific feedback — runs `./run_*.sh` scripts, plays the actual game, and reports issues observed during real play (e.g., "al perder no sono" = game-over sound missing on loss) rather than relying solely on unit tests. Confidence: 0.85
